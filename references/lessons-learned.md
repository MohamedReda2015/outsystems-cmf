# Lessons learned (CLL-*)

From O11 case-management and approval-workflow apps (request portals, back-office approvals, complaint handling) and from recurring CMF community issues. Names are generalized. Each lesson: problem → cause → rule. The source column says whether it comes from public CMF issues (**public**) or from project practice (**project**).

| ID | Source | Lesson |
|---|---|---|
| `CLL-01` | public | **"Status is not valid for the status set."** Causes reported: the status was not linked to the case's definition, two status records shared a GUID after copy-paste, or the status never reached CMF (`CLL-18`). **Rule**: generate every GUID once, validate uniqueness with the validator, register statuses through the bootstrap, and read the definition back after registering (`CDF-02`, `CST-02`). |
| `CLL-02` | public | **The same status worked through `Case_CloseActivity` but failed through `Case_UpdateStatus`** (and code mixing both left status and open activities out of sync). Cause: different paths, state-machine validation, mixed mechanisms. **Rule**: one mechanism per transition, every pair registered in the state machine, read the status back in DEV/TST (`CST-04`, `CST-09`). |
| `CLL-03` | project | **Business status and workflow status drifted.** Screens updated `Request.Status` directly while the workflow moved on its own. **Rule**: CMF owns status; the mirror is written only by the wrapper in the same transaction; a reconciliation timer reports drift (`CST-01`). |
| `CLL-04` | project | **Human activity destinations pointed at Front-End screens from a Core process** → upward reference, Front-End and Core had to be deployed together. **Rule**: no destinations in Core processes; FE routing table by activity key (`CAC-03`). |
| `CLL-05` | project | **Tasks assigned to named users stalled when people left or went on leave.** **Rule**: assign to groups; use claim/reassign wrappers and CMF delegation (`CAC-01`, `CSL-02`). |
| `CLL-06` | project | **Approve/Reject buttons were driven by status on the client**; a user replayed the request on a case they no longer owned. **Rule**: allowed actions from the server, re-checked on submit, plus instance access and ownership (`CAC-02`, `CSC-01`…`CSC-03`). |
| `CLL-07` | project | **"Done" was claimed without walking every transition**; two transitions were missing in production. **Rule**: the spec's transition matrix is the test plan; verify each in the running app (`COP-07`, `BLL-01`). |
| `CLL-08` | project | **Emails were sent inside the activity**; when the transaction rolled back, applicants got "Approved" for a case that wasn't. **Rule**: outbox after commit (`CSL-03`). |
| `CLL-09` | project | **A framework module was edited locally to fix a bug**, and the next framework upgrade overwrote it silently. **Rule**: never edit CMF; work around in the adapter with a comment naming the version (`CAR-02`, `COP-03`). |
| `CLL-10` | project | **Process changed while hundreds of cases were open**; instances on the old version hit removed activities. **Rule**: deactivate, don't delete; a migration plan per change, tested on a production copy (`COP-04`). |
| `CLL-11` | project | **Inbox was slow**: one CMF call per row to get status and assignee. **Rule**: mirror what lists need on the business entity; one paged query per page (`CUI-01`, `BPF-01`). |
| `CLL-12` | project | **Due dates computed in the browser ignored holidays** and differed between users' time zones. **Rule**: CMF SLA with calendars, server-side `DueOn` and `SlaState` (`CSL-01`). |
| `CLL-13` | project | **Holiday calendar wasn't loaded for the new year**; every SLA breached on 1 January. **Rule**: calendar load is an operations checklist item before year end (`CSL-06`, `COP-05`). |
| `CLL-14` | public | **Group-assigned activities were missing from the timeline** on CMF versions before 1.5.3. **Rule**: check the installed version's release notes; test the timeline with group assignment (`CSL-08`). |
| `CLL-15` | project | **Taking every public element of a shared framework module** pulled tenant-specific entities and caused invalid-reference errors (seen with a shared IdP module; same risk with framework modules). **Rule**: reference only the API actions and structures you use (`CAR-01`). |
| `CLL-16` | project | **Seed data for test groups reached production.** **Rule**: seed timers with a kill switch that is empty/off in production (`CDF-05`). |
| `CLL-17` | project | **API names written from memory didn't exist** in the installed framework version. **Rule**: build from the inventory of the installed `_API` modules (`CAR-03`). |
| `CLL-18` | public | **A new status existed in `CaseStatusConfiguration` but CMF still rejected it.** Cause (MVP answer): CMF validates against its own `CaseStatus` data (`CM_CaseDefinition_CS`) filled by the setup action run by the bootstrap timer; the setup had not (re)applied it, and a guard in a sample setup flow skipped re-setup when configuration already existed. **Rule**: after any status change, re-run the bootstrap and verify via `CaseDefinition_GetStatusList`; never trust the static entity alone (`CDF-03`). |
| `CLL-19` | public | **Definition status stayed 0/Loading after bootstrap**, and follow-up configuration (priorities) didn't run. It reached Ready later on its own. **Rule**: setup is asynchronous; the bootstrap verifies Ready and logs `Pending`, and nothing depends on the definition before Ready (`CDF-09`). |
| `CLL-20` | public | **Teams expected the state machine to move the status.** Staff answer: CMF never updates status by itself; `Case_CloseActivity` with an empty Status leaves it unchanged. **Rule**: the wrapper passes the target status from the spec (`CST-08`). |
| `CLL-21` | public | **Lowering a case to Read didn't remove Write**, and `Case_UpdateGroupAccess` raised when used for definition rights. Cause: highest of definition/instance wins; separate actions per level. **Rule**: minimal definition-level grants, per-case grants at instance level, right action per level (`CSC-09`). |
| `CLL-22` | public | **Writes after `Case_CloseActivity` couldn't roll back**: the close commits the transaction (default BPT behaviour). **Rule**: validate and write first, close last, or use `Case_CloseActivityAsync` (`CAC-09`). |
| `CLL-23` | public | **Inbox tabs changed after upgrading to 1.5.1**: *MyActivities* began returning every activity of the user's groups. **Rule**: build tabs with `ActivityAssignementStatusId`; re-test inbox on every upgrade (`CUI-09`). |
| `CLL-24` | public | **Due dates were wrong or null with calendars** (fixed in 1.5.2 for non-working start dates; still reported in 2024). **Rule**: test due dates with weekends, holidays, year change and time zones on your version (`CSL-10`). |
| `CLL-25` | public | **Fetch actions started failing for anonymous/unregistered callers after 1.5.2.** **Rule**: case reads only for registered users; external flows through a registered account or a BL path (`CSC-10`). |
| `CLL-26` | public | **Docs, App Starter and forum used different setup names** (`SetupCaseManagementApplication`, `DEPRECATED_…`, `BootstrapCaseConfiguration`, `Bootstrap_CaseConfiguration`, `Timer_SetupApplication`). **Rule**: inventory first; use the non-deprecated action available in your version (`CAR-03`, `CDF-09`). |
| `CLL-27` | public | **Action bars were empty**: `Activity_GetActionList` returned nothing before 1.5.1. **Rule**: be on 1.5.1+; keep the spec's action list as the base and intersect with CMF (`CAC-02`). |
